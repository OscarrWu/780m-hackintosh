## 2. 阶段定位与目标

### 2.1 总目标与两篇拆分

阶段 4 总目标：点亮内屏 2880×1800@90Hz + 背光可调；WindowServer 识别 IOFramebuffer；为阶段 5 提供扫描输出。

**两篇拆分（项目统一说法）**：

| 篇 | 内容 | 完成标准 |
|---|---|---|
| 4a 显示宿主 | IOFramebuffer 自建、DisplayPipe trampoline、HUBP 表面、GPUWrangler busy-hold、AGDC、DCN 3.1.4 寄存器层、同模式接管与翻页、看门狗与安全网、背光、NVRAM 标记回退 | **"看起来正常的 Mac"**：软件合成下桌面完全可用——开机进桌面、窗口拖动流畅、亮度可调、"关于本机"显示 780M。用户此时已可日常使用（浏览器/文档/终端），只是 App 渲染与合成性能受限 |
| 4b Apple 集成层 | TTL 对象创建、vtable 槽位取证表、xlat11 生成器、HardwareHook GFX11 偏移表、hook 安装、加速器激活 | **IOGraphicsAccelerator2 服务出现**：WindowServer 走正统 Apple 加速器路径做 GPU 合成（IOGraphicsAccelerator2 + xlat 翻译） |

App 的 Metal 渲染接管属阶段 5（《15-阶段5-Metal.md》），不在本阶段。

**合成机制统一说法**：合成走正统 Apple 加速器路径（IOGraphicsAccelerator2 + xlat 翻译），**不走 nullarc 的 Metal 插件路径**。凡涉及 nullarc 度量（CompositorMetal、`debug.nvaccel_iop_ok` 等）的验收表述，一律改为 Apple 路径对应通过标准（IOGraphicsAccelerator2 服务出现、xlat 翻译计数、合成器走加速器），见 6.2。

### 2.2 篇 4a：显示宿主——定位与入口条件

**定位**：RDNA4FB 在 RDNA3 上不可用，其显示宿主角色要自建；显示路线为 **DCN 3.1.4 同模式接管 + 硬件翻页**。依据：固件 GOP 已点亮屏幕并配好显示引擎（阶段 0 取证验证 OTG 在计数、状态可读）；首期验收是固定原生模式，不需要任意 mode-set；同模式接管避免冷启动风险（链路训练/时序由固件完成且验证过）；帧由 GPU 直接扫描，无 CPU 拷贝硬伤。

**进入条件**：

1. 阶段 3 的 compute 闭环通过（GPU 能干活，渲染目标缓冲可写，见《13-阶段3-内存与队列.md》）；
2. 阶段 0 的 DCN 快照与背光取证在手（OTG/HUBP/DIO 状态健康可读、HUBP 表面地址可定位；若取证发现配置不完整，再评估补 mode-set 能力，届时 Linux dcn314 的完整序列是主源）；
3. 显示宿主代码已通过 host 测试；
4. 开工前先产出《阶段4a-需求文档》并经主 agent 验收（沿用阶段 2/3 的需求文档前置流程）。

### 2.3 篇 4b：Apple 集成层——定位与入口条件

**定位**：让 Apple 加速器（`AMDRadeonX6000`）在 780M 上真正工作：TTL 对象创建、Hardware/VMM hook、xlat11 命令翻译、加速器激活。介入点按侵入性从低到高：TTL 槽位（低）→ Hardware/VMM vtable（中）→ 命令流翻译（中）→ 显示宿主/AGDC（中高）→ 自写加速器（高，仅备选）。

**进入条件**：

1. 篇 4a 通过标准达成（桌面软件合成可用，扫描输出稳定）；
2. Apple 侧取证在手：Ventura TTL 43 槽与 Tahoe ABI 逐槽对齐、getTtl 同号 266、Hardware/VMM 槽位表（静态反汇编实测，见 4.2）、TTL 对象运行时创建实证（见 4.1）；
3. 开工前先产出《阶段4b-需求文档》并经主 agent 验收。

## 3. 篇 4a：显示宿主

### 3.1 RDNA4FB 三个角色的替代

| RDNA4FB 的角色 | RDNA3 的替代 | 参考 |
|---|---|---|
| IOFramebuffer 宿主（GOP 延续，`Console,*` 几何） | 自写 IOFramebuffer 子类：boot 时从 `IOPlatformExpert::getConsoleInfo` 拿固件帧缓冲几何，发布为 IOFramebuffer | nullarc `PhxAMDFB` [37]（已实机验证：NVRAM phxfb-boot 标记法、panic 自动回退、GPUWrangler busy-hold 时序） |
| display machine 宿主（pipeadopt 的挂点） | 自写 IOAccelDisplayPipe 子类（trampoline 转发到 bringup kext 的 ops 表） | Cobalt64 `Navi48DisplayPipe`（RDNA4 已验证的结构）[38] |
| 扫描输出缓冲持有者 | DCN 3.1.4 的 HUBP 表面（GPU 直扫） | Cobalt64 disp2 verb 的 RDNA3 版 |

### 3.2 IOFramebuffer 自建

自写 IOFramebuffer 子类：boot 时从 `IOPlatformExpert::getConsoleInfo` 取固件帧缓冲几何（`Console,*` 属性），发布为 IOFramebuffer，延续 GOP 画面。宿主提供模式表（2880×1800@90 至少一项）、VBL/翻页接口。

nullarc `PhxAMDFB` 参照 [37]（对照值，需本机复核）：NVRAM phxfb-boot 标记法、panic 自动回退、GPUWrangler busy-hold 时序——三者的机制设计可参照，其平台相关数值不作本机真值。

### 3.3 DisplayPipe trampoline

自写 IOAccelDisplayPipe 子类作 display machine 宿主（pipeadopt 的挂点），内部以 trampoline 转发到 bringup kext 的 ops 表——结构照 Cobalt64 `Navi48DisplayPipe`（RDNA4 已验证）[38]，寄存器操作换 DCN 3.1.4。

### 3.4 HUBP 表面（GPU 直扫）

扫描输出缓冲由 DCN 3.1.4 的 HUBP 表面持有：渲染目标缓冲的地址写入 HUBP 的 surface 寄存器，GPU 直接扫描输出，无 CPU 拷贝帧进交付路径。

### 3.5 GPUWrangler busy-hold 时序

nullarc 实证的关键坑 [37]：GPUWrangler 在 PCI 设备 quiet 后才探测并记录 framebuffer 的 accelerator；boot 时加速器还没起来，会记"no accelerator"导致软件合成。解法：宿主启动时 busy-hold（`adjustBusy(1)`），boot 守护进程完成 bring-up + arming（武装：启用接管路径的动作）后释放；**120 秒定时器兜底**（失败只损失延迟不损失 boot）。

### 3.6 AGDC

WindowServer 启动时问 AGDC（AppleGraphicsDeviceControl）vendor 命令 0x980 要 framebuffer 列表；没有这个服务就软件合成（且软件渲染器会在 Metal 合成器做的 layer 上 abort）。自建 AGDC 对象：Cobalt64 的 `Navi48AGDC` 结构 [9] + nullarc 的 `PhxAGDC` 实现参照 [37]；**Ventura 的基类布局要重新取证**。

已知取证事实：AGDC 的厂商钩子跨版本移位 1 槽（[266] 纯虚 → [267]=vendor_doDeviceAttribute）——若走 native AGDC 路线需按 Ventura 重定位（阶段 0 静态取证结论）。

### 3.7 DCN 3.1.4 寄存器层

新增 `src/dcn314/` [23]：`dcn314_regs.h`（生成）、`dcn314_allow.c/h`（写白名单）、`dcn314_otg.c`、`dcn314_hubp.c`、`dcn314_dio.c`、`dcn314_aux.c`。生成器复用 `tools/dcn41/` 的（gen_regs/gen_allow/gen_census/gen_modes/gen_dmub_layout），输入换 Linux `dcn_3_1_4_offset.h`。保留写白名单与 host 测试。首期只实现内屏 eDP 最小路径。

**量级说明（校对）**：`dcn314_dio.c`/`dcn314_aux.c` 是**从零实现**而非移植——dcn41 层没有 DIO/DIG/AUX 封装。可直接复用的是 disp2 的编排框架（实例守卫 + 写白名单 + op 预检 + 步骤表 + 50ms DP 扰动验证，IP 无关），步骤表本身按 DCN 3.1.4 重写。

### 3.8 同模式接管与翻页

**步骤**：

1. **只读快照**：读 OTG0 的 H/V total、HUBP0 的表面地址/格式/tiling、DIO 的链路状态（阶段 0 已取，此处复核）；
2. **表面接管**：把渲染目标缓冲的地址写入 HUBP 的 surface 寄存器（翻页 = 更新 surface 地址 + flip pending 确认）；
3. **翻页路径**：WindowServer present → IOAccelDisplayPipe（自建 trampoline）→ N48N scanout selectors → kext 写 HUBP；
4. **验证**：已知图案（颜色条/棋盘格）经 GPU 渲染后上屏；CRC 或读回校验。

**同模式验证（零风险理解性验证，吸收 Cobalt64 的 dcnmode=1 判据）**：把快照值原样写回（write identical back）→ 重新 capture → 逐 dword 比对全部一致；帧计数器继续走（无 stall）。这是"我们理解了 DCN 状态"的证明。

**翻页证据链（witness 5 项，吸收 Cobalt64 的 dcnflip）**：① CRC 前后变化（内容真的换了）② flip pending 置位 ③ EARLIEST_INUSE 更新 ④ 帧计数器继续走 ⑤ 地址恢复原值。5 项全中 = 翻页真实生效。

### 3.9 看门狗与安全网

吸收 Cobalt64 的 scanx watchdog [1]：

- **帧计数器 stall watchdog**：翻页接管后启动看门狗线程，50ms 轮询 OTG 帧计数器；连续无进展 → 立即恢复快照原值（emergency restore）并 latch off 翻页路径——屏幕最多花一瞬，不会黑死。
- **中断风暴保护（storm guard）**：VBL 中断计数超阈值（Cobalt64：20 万）自动关闭中断源，防中断风暴拖死系统。
- **kill file 通道**：`/var/tmp/n48r3-noflip` 存在时内核侧拒绝翻页（调试期的人工急停，对应 Cobalt64 的 `n48m-noflip`）。落点用 `/var/tmp`（macOS 的 `/tmp` 会被清理；基座沿用 `/private/tmp` 的写法在本项目不采用）。
- **健康检查**：`n48r3test health`（30 秒只读轮询：VM fault/HUNG/pid/HUBP underflow）。

### 3.10 背光

实现路线已确定：**由自建显示宿主直接编程 GPU 的 DIO link-encoder PWM 寄存器**。双证据：

1. **反汇编**（Apple 原生驱动二进制的静态反汇编）：Apple 原生驱动的背光实现走寄存器/MMIO——`dce110_edp_backlight_control` 通过 DIO link-encoder 输出 PWM，`dmcu_set_backlight_level` 走 DMCU 邮箱——全代码中**没有 AUX-DPCD 背光路径**；
2. **SSH 实测**：PNLF 是无 _BCL/_BCM/_BQC 方法的壳设备（SSDT 注入的兼容壳，BacklightLevel=unsupported）——ACPI 方法路径在本机不通。

**pwrseq0 实测参数**：enabled=1、level=65536、period=4000、bitcnt=12（阶段 0 运行时取证）。

0b 探针在 DCN 快照时一并读 DIO PWM 寄存器状态（当前亮度值、PWM 频率），确认寄存器可读可定位。实现要点：宿主的 IOFramebuffer 提供亮度 set/get，底层写 DIO PWM 寄存器（寄存器偏移来自 Linux dcn314 头文件）；与 DCN 同模式接管共用同一套寄存器基址。

## 4. 篇 4b：Apple 集成层

### 4.1 TTL 对象创建

**已实证事实（阶段 0 取证，本机实测）**：

- TTL 机制存在：`AmdTtlServices` 是无名 C++ 类（2880 字节、无 RTTI/OSMetaClass），43 个槽位与 Cobalt64 的 `AmdTtlServicesABI.h` 逐槽 1:1 对齐（用 slot 24/25 的 0xE00002C7 stub 指纹做了字节级验证）——Cobalt64 的 TTL ABI 头可直接作为 780M 的 TTL 契约；
- **TTL 对象两次 boot 实测创建成功**：getTtl 返回非空内核堆指针；TTL 对象 vptr 与静态取证 vtable 地址精确对应——**vptr = HWLibs 运行时基址 + 0x402968**（slide 每次重启变化但偏移关系恒定）；
- getTtl 槽位与 Tahoe 相同（slot 266，Navi/SWIP 两张 vtable 各 270 槽的第 266 格指向 `AMDRadeonHWServicesSWIP::getTtl`）；锚点几何已运行时验证（slot 269=getMatchProperty@0x1630 两次 boot 精确对应）；
- generation-agnostic 成立（高置信度）：全 kext 唯一的 MMIO 写入口是 `AMDHWRegisters::write`（TTL slot 36），寄存器基址全部来自 TTL slot 11 的查询——加速器自己不认识 GFX11 寄存器，只通过 TTL 摸硬件；置信度边界：静态覆盖了符号可见的全部写路径，运行时终验留给 0b 探针；
- **前置问题**：HWLibs kext start 早期 `populateFirmwareDirectory` 的 84 项设备 ID 表查 0x15BF 失败 → 固件目录内容不完整（报错不阻断 TTL 对象创建，但影响后续固件查询）——阶段 4b 的 TTL 实现（NaviR3Ttl 的 setFirmwareDirectory slot 8）必须解决此前置。

| 同号 | 62 | flushHDP | |

### 4.3 xlat11 命令流翻译生成器

Apple 发出 GFX10.3（RDNA2）方言的 PM4 命令流，翻译器逐条查表改写成 GFX11 方言。**六类规则**：identical / moved / field_repack / absent / reused / legacy_vs。表源 Mesa 寄存器库 gfx103（对照 xlat12 的生成模式：`gfx103.json`+`gfx12.json` 固定 commit 4519cc56、reused 表手写 2 条映射约 72 行 [6]；xlat11 的具体输入 JSON 组合待取证，按 xlat12 模式生成）。

**xlat11 不是"换一张表"**：GFX11 只有 NGG 顶点路径（与 GFX12 同规则，可复用审查方法）、scissor 的 BR 语义、reused 同地址覆盖、字段映射差异。表可生成，规则逐条审。GFX11 与 GFX12 同样只有 NGG 顶点路径，legacy VS 走拒绝规则（legacy_vs）。

### 4.4 HardwareHook GFX11 偏移表与 hook 安装

**为什么需要 hook**：Apple 上层有少数高频捷径（刷缓存、失效页表）把 GFX10 的寄存器地址写死在代码里——在 Apple 自己的世界里上下层永远配套，这是合理优化；Cobalt64 换掉下层后前提被打破，所以 hook `Hardware`/`VMM` 的相关槽位 [5]：62 flushHDP、93 getVmm、102 registerChannel、187 allocHWRegs、191 setVMRegs、247/248 hub、36 regWrite 与 35 regRead（MMIO 读路径同样被拦截并走影子缓存，源码校对补记）、VMM 71 programAndInvalidate。

**GFX11 偏移表**：hook 拦截到的 GFX10 偏移写需按 GFX11 偏移表改写（偏移来源：Linux `gc_11_0_0_offset.h` 等，见《00-总体路线.md》附录 B）。**GFX11 偏移映射表待取证**：RDNA3 场景下哪些 GFX10 偏移需要映射、映射到哪个 GFX11 偏移，须在 4b 开工时按 Linux/Mesa 源码逐条取证，不得猜测。

**hook 安装**：复制 vtable、替换槽位的运行时操作——槽位号对不上一格就会 hook 到错误函数，轻则功能缺失重则内核挂死（Cobalt64 在 Tahoe 上 0.0.52 的真实教训 [1]）。因此 4.2 的槽位表必须先经运行时验证，再安装 hook。

### 4.5 加速器激活与 GPU 合成

**目标**：加速器激活后，WindowServer 经 IOGraphicsAccelerator2 走正统 Apple 加速器路径做 GPU 合成。

**合成机制统一说法**：走正统 Apple 加速器路径（IOGraphicsAccelerator2 + xlat 翻译），不走 nullarc 的 Metal 插件路径。验收标准（替代 nullarc 的 CompositorMetal/`debug.nvaccel_iop_ok` 度量）：

1. **IOGraphicsAccelerator2 服务出现**（`ioreg` 可见）；
2. **xlat 翻译计数**（翻译器实际处理命令流的计数增长）；
3. **合成器走加速器**（WindowServer 的合成路径经加速器，无软件渲染 abort）。

**已知前置**（阶段 0 探针实证）：加速器激活路径曾出现 init 失败链（SMU SW_INIT 失败 → SWIP failed → TLS failed → 0x4 → 0xe00002bc → 全链卸载回 GOP）——该失败发生在阶段 0 的无驱动上下文；阶段 2 已完成上电与固件，阶段 4b 在驱动就绪上下文中激活，此失败链不应复现，若复现按失败处理流程定位。另：加速器激活曾是 Wi-Fi 干扰源（阶段 0 v1 部署实证），4b 验证时注意观察。

## 7. 风险与回退

| 风险 ID | 风险 | 概率/影响 | 缓解与回退 |
|---|---|---|---|
| R4 | DCN 3.1.4 同模式接管失败（GOP 状态不健康/翻页写错） | 中 / 中 | 阶段 0 快照取证；只读先行；boot-arg 回退；必要时补 mode-set |
| R5 | GPU hang 整机无响应 | 中 / 高 | 默认关闭 + 超时 + latch off + NVRAM 标记自动回退 + 人工恢复 |
| R10 | 面板实际不是 90Hz/需 DSC | 低 / 中 | 以 EDID 为准（本机实测 2880×1800@90.006Hz）；DSC 路径预留 |
| R12 | DIO PWM 寄存器与预期不符（如需 DMCU 邮箱协作） | 低 / 低 | 0b 探针已读 DIO PWM 状态确认可读可定位；DMCU 路径保留备选 |
| R14（新增） | 4b 槽位取证失败（运行时验证不通过） | 中 / 中 | 回退纯软件合成路线：停在 4a 完成标准（桌面软件合成可用），4b 重新取证后再启动 |
| R15（新增） | xlat11 规则覆盖不全（翻译缺规则导致渲染异常） | 中 / 中 | 按 Mesa 增量补充规则；host test 的 fuzz/golden 兜底；缺规则时 latch off 加速器路径退回软件合成 |

**boot-arg 回退**：`n48r3-dcn=0`（不接管 DCN，宿主退回纯 GOP 延续——屏幕回到固件画面，系统可用）；`n48r3bringup=0`（整体不加载）；kill file `/var/tmp/n48r3-noflip`（人工急停翻页）。NVRAM 标记法（nullarc phxboot 实证 [37]）：本次 boot 显示失败 → 写 NVRAM 标记 → 下次 boot 自动跳过显示接管，直接用固件帧缓冲。点亮失败：`n48r3test dcnstate` 对照快照逐寄存器定位差异。
